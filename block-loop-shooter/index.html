Overview

Block Loop Shooter is a portrait puzzle game. A train of coloured blocks runs around a closed loop. The player sends shooters from a pit to four pads in front of the loop; each shooter fires at the blocks of its own colour as they pass. Clear every block to win; let every pad fill with shooters that can no longer hit anything and the attempt is lost.

The package contains the playable game with 500 levels, three boosters (Swap, Pad +, Burst), a visual level editor and a seeded level generator, and the HyperCasualLiveOpsKit shell (menu, results, coins, shop, booster bar and refill offer). The first level and level 200 are the two authored levels of the campaign, written directly as level files; the other 498 levels were made by the generator that ships in this package.

Getting Started

Requirements

  • Unity 6000.0.62f1 (Unity 6). Other versions were not tested.
  • Packages: Universal RP com.unity.render-pipelines.universal 17.0.4, Input System com.unity.inputsystem 1.14.2, Unity UI com.unity.ugui 2.0.0 (it carries TextMesh Pro), and the built-in modules of a Universal 3D project.
  • TMP Essential Resources (Window → TextMeshPro → Import TMP Essential Resources). The game uses Unity's default fonts only: the TMP default font asset and the built-in LegacyRuntime.ttf. No font file ships in this package.

Import into a new project

  1. Create a new Universal 3D project in Unity 6000.0.62f1 and install the three packages above at those versions (Window → Package Manager).
  2. Import TMP Essential Resources and keep their default location Assets/TextMesh Pro.
  3. Import Block-Loop-Shooter-v3.unitypackage (Assets → Import Package → Custom Package, import everything). It creates exactly two folders: Assets/Game and Assets/HyperCasualLiveOpsKit. Wait for compilation to finish.
  4. Edit → Project Settings → Player → Other Settings → Active Input Handling: Input System Package (New) or Both.
  5. Edit → Project Settings → Graphics: set the Default Render Pipeline to Assets/Game/ProjectRenderSettings/PC_RPAsset.asset. In Quality, set the same asset as the Render Pipeline Asset of every quality level you use. Keep the Color Space on Linear (Player → Other Settings).
  6. File → Build Profiles (Build Settings): add Assets/HyperCasualLiveOpsKit/StarterMenu/Scenes/HLK_MainMenu.unity first and Assets/Game/Scenes/Game.unity second. The menu scene opens the gameplay scene by its name Game.
  7. Open HLK_MainMenu.unity and press Play. Close the welcome card, press PLAY: level 1 opens with a short lesson.

A unitypackage carries assets only, never Project Settings: steps 4 to 6 are yours to make in every new project. The clean-import test of this package made the same settings in a new empty project (only the three packages and Unity's built-in modules, TMP Essentials, then this package), built a Windows development player from the two scenes and played it from the menu.

Gameplay

  • The loop. A rigid train of rows, five blocks wide, moves around the loop at the level's speed. The straight bottom part in front of the pads is the firing stretch.
  • Sending a shooter. Tap a shooter in the pit. A shooter can leave when empty cells connect it to the top of the pit; it jumps to the leftmost free pad. Tapping a shooter that is still enclosed only makes it nudge. When all pads are busy, hold the press: the shooter leaves as soon as a pad frees; releasing first cancels it.
  • Firing. A shooter on a pad fires at the frontmost block of its colour inside the firing stretch, one block per shot, 100 shots per shooter (20 rows of five blocks). Empty, it leaves and frees its pad. When several shooters of one colour are parked, only the leftmost fires.
  • Hidden shooters show a question mark until they are uncovered; their colour is revealed when empty cells connect them to the top of the pit.
  • Dispenser boxes hold a queue of shooters and release the next one into the cell on their open side whenever that cell is empty.
  • Feeder lanes carry rows of blocks that drop into the loop: a row passing the lane's junction takes the lane's next row when it is completely empty.
  • End game. From level 4 on (level 200 included), the train speeds up once the pit has no shooter left.
  • Win. Every block on the loop and in the feeder lanes is cleared and every shooter has left. The kit's win card opens and 50 coins are credited once.
  • Loss. With every pad occupied, a full lap with no shot and no row fed ends the attempt; so does a jam: every pad occupied for two laps (plus one second) with fewer than 1.5 blocks shot per second. The kit's lose card offers TRY AGAIN, which loads a fresh board of the same level (a mock interstitial ad may show first in the LocalQA profile). A loss costs nothing and earns nothing.
  • Lesson. Level 1 shows a tutorial hand and one sentence; a booster's first use shows its explanation card once.

Campaign

500 levels in seven chapters starting at levels 1, 21, 61, 121, 201, 301 and 401. Each level combines a loop silhouette (square, stadium, arch, oval, heart, horseshoe, bell and others), zero to two feeder lanes and a pit outline, and introduces its mechanics in order: the first feeder lane on level 3, two feeder lanes on level 8, hidden shooters on level 10, the first dispenser box on level 16. Later chapters raise the number of cells, colours, hidden shooters and boxes; recovery levels in between are easier. The first level and level 200 are authored levels.

Every level file stores a winning tap list (its witness; the two authored levels keep theirs in CampaignAuthoring.json). The editor and the generator refuse to save a level whose witness does not win on the game's own simulation, both as the game runs it and as the kit shell builds it.

Coins and Saves

A win credits 50 coins (WinCoinReward in Assets/HyperCasualLiveOpsKit/StarterMenu/Resources/HLK/StarterMenuConfig.asset). Progress (completed levels), coins and booster charges are saved locally by the kit (Unity PlayerPrefs, under your Player Settings company and product name) and survive a restart; the menu's PLAY opens the next unfinished level. Opening a level by number (the DEV level picker of development builds) does not change saved progress. The shop, wheel, chests, quests and other kit screens are described in the kit's own guide (Assets/HyperCasualLiveOpsKit/Documentation/Documentation.html).

Level Editor

Tools → Block Loop Shooter → Level Editor opens the window BlockLoop Levels on the saved campaign (found by its CampaignAuthoring.json).

  • Top row: Undo (also Ctrl+Z, 64 steps), Reload (discards unsaved edits), Validate + save.
  • Left list: Level 1 to Level 500. Level buttons: Duplicate, Delete, Up, Down (levels are renumbered).
  • Canvas: the loop (white), feeder lanes, pads (circles) and the pit cells in their colours; ? marks a hidden shooter, <3 or >3 a box with its direction and queue length. Drag a yellow handle to move a control point of the loop: every runtime field is rebuilt from the layout and the witness is cleared. Rebuild + find witness (lower left) derives the level from its layout block again and searches a winning tap list with the game's simulation. The two authored levels (the first level and level 200) are shown as text only.
  • Exact game data: the level's JSON. Apply data edit (invalidates witness) takes your text; Validate selected checks the level rules and replays the witness; Play saved level opens Game.unity on that level in Play mode (save first).

Saving: Validate + save checks the whole campaign (count equal to the saved request, contiguous numbering, every level's rules and witness on both simulations, no duplicate puzzle, no more than two equal formations in a row, at least the minimum number of formations, the chapter plan) and only then replaces Assets/Game/Campaign/Resources/Levels in one step. A failed check changes no file and shows the reason. The previous folder is kept as a backup in LevelToolBackups of your project (outside Assets) and the request in ProjectSettings/LevelTools/BlockLoop.json. Checking all 500 levels takes about two minutes on a desktop CPU.

Worked Example: edit, validate, save, play

Make the loop of level 3 lower by one row of the world grid. This exact edit was made in a new project with this package and checked as described.

  1. Open Tools → Block Loop Shooter → Level Editor and select Level 3 (a stadium loop of 64 rows, one diagonal feeder lane, five shooters).
  2. In Exact game data, find the layout's control polygon: 
    "control": [[-11.925, 0, 6.615], [11.925, 0, 6.615], [11.925, 13.5, 6.615], [-11.925, 13.5, 6.615]],
    and change the two top points from 13.5 to 12.5: 
    "control": [[-11.925, 0, 6.615], [11.925, 0, 6.615], [11.925, 12.5, 6.615], [-11.925, 12.5, 6.615]],
  3. Press Apply data edit (invalidates witness). The canvas says the level has no witness and cannot be saved.
  4. Press Rebuild + find witness. The level is rebuilt from its layout: the loop now has 62 rows instead of 64, the extra rows of blocks move to the feeder lane, and a new witness is found: 60:1.1 90:1.2 120:1.3 150:2.2 1101:2.3 (five taps; each tap is step:row.column, a step being 10 ms).
  5. Press Validate selected: "Selected level model + witness passed."
  6. Press Validate + save: Level_3.json and CampaignAuthoring.json are written after the whole campaign passed.
  7. Press Play saved level (or start from HLK_MainMenu): level 3 runs on the shorter loop. In the clean-import test the saved file was what the game loaded, and the new witness won it on the simulation the kit shell plays.
  8. To undo the example: Undo before saving, or set the values back to 13.5, rebuild, find witness and save again (that test then restored the shipped campaign byte for byte).

Edits that fail are explained in the status line, for example a loop that leaves the board (rule G15), two stretches closer than one track width (G1), or blocks and shots of a colour that do not match (G8).

Example: append two levels

  1. Set Final campaign count to 502, keep Seed 20261013, tick Append to saved campaign.
  2. Press Generate into editor. This takes under a minute on a desktop CPU (plus about two minutes the first time the window checks all 500 saved levels). Levels 1 to 500 stay exactly as they were. Level 501 is a mushroom loop with two diagonal feeder lanes; level 502 a bell loop with a diagonal and a rail feeder lane; each comes with its own witness.
  3. Review them on the canvas, then press Validate + save: Level_501.json and Level_502.json are written and the game counts 502 levels. Set VisibleLevelCount in StarterMenuConfig.asset to the new count if the menu should show them.

The clean-import test generated, validated and saved exactly this append, then saved the shipped 500 levels back. Replace mode drafts every level one after another in the window (tens of seconds per level), so regenerating all 500 takes hours; it was not part of the test. The two authored levels (the first level and level 200) are never generated: replace mode keeps their files and finds their witness again.

FieldMeaning
id, title, numberIdentity; number is the level number shown by the shell.
aspectWidth / height of the board the normalised coordinates refer to; the camera fit keeps it visible in any portrait window.
coinsText, reward, rewardX2, newFeature, tutorialText, nextRectUsed only by the game's built-in result screen and HUD. Under the kit shell (the shipped flow) the win reward is WinCoinReward and the kit's cards are shown.
coloursThe level's palette: name (referenced everywhere below) and hex colour.
track.shapeSilhouette name (informative).
track.rows, lanesRows on the loop and blocks per row (5). loop must add up to rows.
track.rowsPerSecondTrain speed.
track.stretchEntryU, stretchRowsWhere the firing stretch starts on the loop (in rows) and how long it is.
track.fireRate, fireRampSeconds, fireRampStart, fireDelay, cubeRemoveDelayShots per second, the ramp from fireRampStart × rate to full rate, the delay before a parked shooter's first shot, and how long a hit block stays visible.
track.halfWidth, centrelineTrack half width and the loop's centre line: points [x, y, u] in normalised screen coordinates with u the distance along the loop in rows.
track.loopThe blocks on the loop at the start, as runs {"colour", "rows"} from row 0; colour "empty" leaves rows empty.
track.feedersFeeder lanes: id (TL top left, TR top right), junction u on the loop, runs of rows waiting in the lane (front first), the lane's drawn path.
pads, padRadius, extraPad (optional)The four pad centres and their radius. Pad + opens a fifth pad next in the row (or at extraPad when given).
pit.cols, rows, x0, y0, dx, dyThe pit grid: size, centre of cell (row 1, column 1) and the cell pitch. Row 1 is the top (mouth) row.
pit.cellsOccupied cells: kind shooter or hidden with a colour (optional ammo, default 100), or box with dir (−1 releases to the left, 1 to the right) and a queue of colours. Missing cells are empty.
timingBoard entry animation and when input starts (inputFrom seconds), shooter jump and exit times, pad and box release delays, the delay before the result.
tutorialThe built-in tutorial hand (on for the first level only).
endgameTrain speed multiplier, ramp and fire multiplier once the pit is empty; praise shows praise words.
layoutThe generator's description the runtime fields are derived from: seed, chapter, role, board class, silhouette, the loop family and signature computed from its shape, pit family and outline, formation key, the loop's control polygon ([x, z, corner radius] in world rows), the feeders (side −1 left / 1 right and kind), and the stream of runs as colourIndex x rows. The game ignores it; the editor rebuilds the level from it.

noteA free note: on generated levels the generator's note with the seed, on the two authored levels a short description. Nothing reads it.

CampaignAuthoring.json in the same folder lists every level (index, formation, payload = the file's exact text, witness) with the saved request; the tools compare it with the files before every save. The two authored levels are the generator's anchor levels: it plans the campaign around them and never regenerates them, and their formation keys start with anchor-oval (level 1) and anchor-heart (level 200).

Customization

  • Levels: through the level window only (see above). New colours must be added to a level's colours and used consistently by loop, feeders and pit; the generator uses the twelve colours of level 200.
  • Boosters: names, explanation texts, the three step chips, icon, first-use picture, StartingCount and UnlockLevel in the three assets of Assets/Game/Integration/PowerUps; unlocks, free charges and prices in BoosterProgression.json. Icons and pictures are in Assets/Game/UI/Boosters.
  • Rewards and menu: StarterMenuConfig.asset (WinCoinReward 50, VisibleLevelCount 500, gameplay scene name Game).
  • Look: materials in Assets/Game/Resources/Materials, shaders in Assets/Game/Shaders, post-processing in Assets/Game/ProjectRenderSettings. The procedural model set is the default; the two generated alternate sets are kept for the game's own built-in flow only.
  • Your identity: set company name, product name, application id and icons in Player Settings. In Assets/HyperCasualLiveOpsKit/Resources/HLK/HLKSettings.asset the rate prompt's Android package name ships as com.ragendom.blockloopshooter (the producer's development id): set it to your own application id, and set your share address, ad and purchase identifiers and privacy links before a release.
  • DEV controls: the DEV button and panel (choose level, reload level, test win and lose, ad and banner tests, save snapshot) exist only in the editor and in development builds; a release build does not show them.

Limitations

  • Tested: Windows desktop (editor, development player at 540 × 960 and other portrait sizes) and the clean import of this package with its tools and a played journey: wins on levels 1 to 16, 250 and 483, the loss on level 28 with TRY AGAIN, and each booster used and the level then won. An Android package was built from the producer project but has not been run on a device (notches, back button, lifecycle and performance on phones are unverified).
  • LocalQA profile: ads are labelled mock ads and purchases are local test flows. No live ad network, store billing, receipt validation, consent flow or privacy policy is configured; these are yours before a store release.
  • Sound: the game uses the kit's sound effects; a listening review on devices was not done. There is no music.
  • Presentation: at window shapes other than a level's own aspect, darker bands lie above and below or beside the board.
  • Not built: a fifth pad as level data (only the Pad + booster opens one), pits deeper than five rows, boxes opening upward, numbered or iridescent blocks, a hard-level banner.
  • Built-in flow: the game still contains its own single-scene flow (own HUD, result screen, model switch on M, debug overlay on F1, Esc / R / L keys, the three helpers with one charge on level 200 only). It is used only when Game.unity runs without the kit shell; under the shell those keys and screens are off.
  • Authored levels: the first level and level 200 have no layout block, so the level editor shows them as text and the generator never redrafts them. The generator takes its twelve colours from level 200. The other 498 levels are generated.
  • AI record: see AI Disclosure; section 4 lists the 2D art files that carry no AI record.
