IAP fulfillment: your choice

Open Tools > HLK > V2 > Game Build Setup. Enable IAP Test or Production, install Unity IAP, assign your catalog and select a fulfillment button. Test uses a real store on device when UseFakeStoreOnDevice is off; only Play's account/distribution setup determines test billing.

Choice Required setup Behavior
ClientSide Real store SDK, matching product IDs, reward hooks Delivers locally without custom receipt validation. No backend needed.
LocalReceiptValidation Above plus Google Play licensing public key Official Unity IAP verifier checks signed Android Google Play receipt, product, transaction and purchased state before local delivery.
ServerAuthoritative HTTPS validator, authenticated session and authoritative ledger Grants are committed by the server. No local fallback or duplicate local reward.

ClientSide is supported in normal signed Release AAB builds. It is not a showcase bypass. Build Doctor warns about local trust rather than demanding a server. Selected but broken integrations still fail preflight. Never use dummy purchases as evidence of real billing.

Existing projects are preserved

New IAP Pro settings resolve to client-side fulfillment. Existing serialized EnableServerValidation = true settings continue resolving to server-authoritative through LegacySettings. Explicit fulfillment selection takes precedence over that legacy checkbox. Switching to ClientSide is deliberate; the builder never changes this choice or erases endpoints.

Deliver first, acknowledge afterward

Local delivery requires a transaction ID and reward hook. A device-local journal tracks pending/delivered transactions. Built-in currency rewards persist the currency balance and processed credit IDs together. Restore recovers receipt-bearing pending orders (including consumables) through the same fulfillment gate; confirmed consumables are not re-granted. Store acknowledgement happens only after successful delivery. Confirmation failures leave store recovery available.

The journal is duplicate protection, not fraud protection. Clearing app data, tampering, reinstalling, switching devices, or a storage failure can defeat device-local history. Server authority is recommended for valuable economies and cross-device accounting. Local signature verification does not continuously detect refunds or revoked entitlements.

Use purchase reward hooks for fulfillment. Purchase events are notifications and may repeat during recovery: do not separately grant currency from those events.

Custom rewards and recovery

Custom hooks must throw if delivery fails, not silently return. Hooks implementing IIdempotentPurchaseReward promise durable transaction-keyed idempotency: use PurchaseGrantContext.TransactionId, commit before returning, and handle replay without another grant. Composite hooks receive distinct child keys. Do not reorder composite children while purchases are pending.

If a non-idempotent custom hook is interrupted after the pending journal write, automatic replay stops for reconciliation rather than risk a second grant. Investigate the transaction and reward state, repair the hook or reconcile through your own support tooling. Do not blindly delete pending journal entries. This asset does not provide a universal reconciliation backend for arbitrary custom rewards.

Subscriptions

Basic local fulfillment is intended for consumables and non-consumables. Real subscription grants require an unexpired store-provided expiry through IStoreBackend.TryGetProductInfo; the current Unity IAP adapter does not expose that expiry. Therefore use the authoritative server integration or a custom backend supplying verified expiry for subscription fulfillment. HLK does not invent a renewal period from an authored demo duration for a real purchase. Missing expiry keeps a local subscription pending instead of acknowledging an undelivered entitlement.

Local Google Play verification

Use the Google Play licensing PUBLIC key, never a service-account/private key. The built-in verifier is Android-device-only; the Editor and other platforms return inconclusive instead of simulated approval. Apps requiring other local verifiers can register ILocalReceiptValidator with HLK services and must supply platform-specific setup/preflight support. A generic server IReceiptValidator is not substituted for a local verifier.

The adapter was checked against Unity IAP 5.4.3. Verification failure or mismatched evidence leaves the transaction unacknowledged. A base64 key passing editor checks is not proof that it matches your app: test a Play-distributed licensed purchase on a real device.

Minimum device acceptance checklist

  1. Build a signed, non-development AAB through Build Game AAB (Google Play) with only needed modules enabled.
  2. Distribute using your Play test track, approved product IDs and license testers. Confirm the native store dialog.
  3. Complete/cancel/defer a purchase. Confirm cancellation never grants, success grants once and pending approval does not grant early.
  4. Relaunch/recover around delivery and acknowledgement. Verify no duplicate currency and restored non-consumable access.
  5. For local signatures, test valid and deliberately wrong licensing keys. For server mode, test rejection/offline recovery and no client fallback.
  6. Verify restore, refunds/revocations and subscription lifecycle according to your selected architecture. Build and automated tests alone do not certify these store/device flows.
