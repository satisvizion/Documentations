Android setup and release readiness (Unity 6000.0.62f1)

This is the Android customer path after importing HLK into a clean Unity 6 URP project. “Build Doctor passes” means only that locally inspectable evidence is coherent. It cannot certify provider-console state, store products, signing fingerprints, consent-message publication, ad serving, device delivery, or Google Play review.

1. Establish the Android player identity

  1. Switch the editor to Android before adding target-specific defines.
  2. In Player Settings, set the final reverse-DNS application ID. Use the same ID in Firebase, Google Play Console, Play Games Services, ads dashboards, and HLKSettings.RateUs.AndroidPackageName.
  3. Enable ARM64. Set Target API Level explicitly to API 36 or newer and install that SDK through Unity Hub. As of 31 August 2026, new Google Play apps and updates must target Android 16/API 36: https://support.google.com/googleplay/android-developer/answer/11926878.
  4. Keep com.unity.modules.androidjni, com.unity.modules.unitywebrequest, and the modules used by your chosen features in Packages/manifest.json.
  5. Configure production keystore/signing outside the package. Do not store passwords, service-account JSON, store secrets, or receipt-validation secrets in Unity assets or source control.

The bundled Android library declares minSdk 23, compileSdk 36, targetSdk 36, VIBRATE, and an app-scoped, non-exported FileProvider. The consuming application still controls the final merged manifest and player SDK levels.

For Firebase, download the Android app’s google-services.json and place it exactly at Assets/google-services.json. The build check parses only client_info.android_client_info.package_name, compares it to Player Settings, and never prints config values. Firebase’s setup guide explains the platform file and Google Services processing: https://firebase.google.com/docs/unity/setup.

Android 13/API 33 and newer require runtime POST_NOTIFICATIONS permission for non-exempt notifications. HLK warns when both notification auto-request options are off; an intentional, app-owned request flow is also valid and must be tested: https://developer.android.com/develop/ui/views/notifications/notification-permission.

3. Manifest, dependency and minification verification

After resolving Android dependencies, export a Gradle project or build an AAB and inspect the merged application manifest, dependency graph, and mapping output. Source-file presence is not proof of a successful merge.

  • Confirm the FileProvider authority resolves to <applicationId>.hlk.sharefiles, exported=false, grantUriPermissions=true, and the paths resource exposes only cache-path.
  • Confirm sharing an actual screenshot produces a content:// URI and the receiving app can read it. Attachment failure must surface as a failure; it must not silently fall back to text-only sharing.
  • Confirm android.permission.VIBRATE and the notification/advertising permissions required by the chosen SDK versions appear in the merged manifest. Do not add unrelated permissions pre-emptively.
  • If minification is enabled, confirm the androidlib’s consumerProguardFiles is applied and dev.hce.sharing.HlkShareBridge remains in the release artifact.
  • Run External Dependency Manager resolution and verify review:2.0.2 and, when selected, app-update:2.1.0. Provider SDKs may impose newer minimum SDKs than HLK’s base library.

4. Preflight and tests

PowerShell examples (adjust the Unity path if Hub is installed elsewhere):

$unity = 'C:\Program Files\Unity\Hub\Editor\6000.0.62f1\Editor\Unity.exe'
$project = 'C:\path\to\your\clean-import-project'

& $unity -batchmode -nographics -quit -projectPath $project -buildTarget Android `
  -executeMethod HLK.Editor.HlkV2BuildDoctor.RunBatch --hlk-production `
  --hlk-output Artifacts/HLK-Android-Doctor -logFile Artifacts/hlk-android-doctor.log

& $unity -batchmode -nographics -quit -projectPath $project -buildTarget Android `
  -runTests -testPlatform EditMode `
  -testFilter HLK.Tests.EditorV2.HlkAndroidReadinessTests `
  -testResults Artifacts/hlk-android-readiness.xml `
  -logFile Artifacts/hlk-android-readiness.log

The package’s showcase build is a local sample/simulator artifact and deliberately uses a scoped non-production doctor profile. It is not a store-release certification. After the production doctor passes, invoke the game’s own CI build method without the showcase scope, create a signed AAB, run Play pre-launch reports, and execute real-device tests for sign-in, purchases (license testers), ads test devices, consent-region variants, notification permission states, cold-start push/deep links, share attachments, WebView allow-list behavior, Saved Games conflicts, attribution deep links, review/update eligibility, process death, offline recovery, and account switching.

5. Expected failure behavior

Explicit production/native selections must fail closed when their dependency is missing. Dummy/simulated modes remain useful for editor and QA. A successful dummy operation is never provider evidence. Build Doctor findings use stable HLKA### rule IDs and become blockers only in the production profile; the Android 13 notification prompt timing rule remains a warning because applications may own that UX outside HLK.
